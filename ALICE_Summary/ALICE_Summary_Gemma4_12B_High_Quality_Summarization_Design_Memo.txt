ALICE_Summary 設計メモ
Gemma 4:12Bで高精度な会話要約を目指すための処理フローとプロンプト例

作成日: 2026-08-20
位置づけ: Project_ALICE / ALICE_Summary 検討用メモ


============================================================
1. 背景・目的
============================================================

目的は、音声文字起こしデータから、ChatGPTによる今回の面談要約に近い精度の
「内容理解を伴う要約」を、ローカルLLMであるGemma 4:12Bに実行させることである。

単純な要約ではなく、以下を実現することを目標とする。

・長時間の会話全体の目的と流れを把握する
・主要な議題を抽出する
・誤変換や発言者分離の乱れを、文脈から明確に判断できる範囲で補正する
・「事実」「本人の説明・認識」「面談者側の指摘・評価」を区別する
・同じ話題について繰り返された会話を統合する
・後半で訂正・修正された内容を反映する
・本題と無関係な雑談を除外する
・面談全体を通じた共通課題や構造を抽出する
・人間が面談に参加していなくても理解できる形に再構成する

重要なのは、「文字起こし → 短縮」ではなく、
「文字起こし → 内容理解 → 構造化 → 要約」
という処理として考えることである。


============================================================
2. 基本方針
============================================================

Gemma 4:12Bに、長時間かつ品質の荒い文字起こしを渡して一度に
「正確な要約を作成してください」
と指示するだけでは、以下の問題が起きる可能性がある。

・前半の重要な情報が後半で失われる
・議題ごとの情報が混ざる
・本人の発言と面談者の評価が混同される
・AI自身の推測が事実として出力される
・後半で訂正された内容が反映されない
・雑談が要約に混入する
・重要な論点が抜け落ちる

そのため、処理を最低2段階に分ける。

推奨フロー:

Transcript
    ↓
[Step 1] Conversation Analysis / 会話理解・構造化
    ↓
structured_summary.json
    ↓
[Step 2] Summary Generation / 人間向け要約生成
    ↓
draft_summary.md
    ↓
[重要案件のみ]
[Step 3] Consistency Check / 原文との整合性確認
    ↓
final_summary.md


============================================================
3. 推奨アーキテクチャ
============================================================

ALICE_Transcript
    │
    │ transcript.json
    ▼
ALICE_Summary
    │
    ├── Step 1: Analyzer
    │      ・会話目的の把握
    │      ・議題抽出
    │      ・文脈理解
    │      ・事実/認識/評価の分離
    │      ・繰り返し論点の統合
    │      ・決定事項/対応事項の抽出
    │      ・不明点の明示
    │
    ▼
summary.json
    │
    ├── Step 2: Generator
    │      ・人間向け要約
    │      ・会話全体の再構成
    │
    ▼
draft_summary.md
    │
    └── Step 3: Checker（必要時）
           ・原文との整合性確認
           ・幻覚/追加事実の検出
           ・発言者や評価の混同確認
           ・重要事項の欠落確認
           ↓
        final_summary.md


============================================================
4. Step 1: 会話理解・構造化
============================================================

この段階では、読みやすい最終文章を作らない。

目的は、
「Gemmaがこの会話で何が起きていたのかを正しく理解した結果」
を構造化データとして残すことである。

この中間結果が、後段のMinute、Memory、Task、Insight等でも利用できる可能性がある。

推奨プロンプト例:

------------------------------------------------------------
あなたは、音声文字起こしから面談内容を正確に理解・整理するAIです。

以下の文字起こしを分析してください。

この文字起こしには、
- 音声認識による誤変換
- 聞き取り不明な箇所
- 発言者分離の誤り
- 文の途中欠落
- 同じ内容の繰り返し
- 本題と関係のない雑談

が含まれている可能性があります。

文脈から明確に判断できる誤変換のみ補正してください。
判断できない内容は推測で補完してはいけません。

この段階では、読みやすい要約文を作成することが目的ではありません。
まず、面談の内容を正確に理解し、後続処理で利用できるよう詳細に構造化してください。

以下を抽出してください。

1. 面談の目的
2. 面談で扱われた主要な議題
3. 各議題について
   - 何が問題として取り上げられたか
   - 確認された事実
   - 本人の説明・認識
   - 面談者側の質問・指摘・評価
   - 原因や背景として話し合われた内容
   - 本人が最終的に認識した内容
   - 改善策や今後の対応
4. 面談の終盤で改めて確認・修正された内容
5. 面談全体を通じて繰り返し現れる共通の課題
6. 次回以降に確認すること
7. 文字起こし上、不明確または判断できない点

重要なルール:

- 「事実」「本人の発言」「面談者の発言」「AIによる分析」を混同しない
- 本人が実際には認めていないことを、本人の認識として書かない
- 面談者が指摘した内容を、客観的事実として書かない
- 後半で発言内容が修正・訂正されている場合は、最終的な認識を優先する
- 同じ議題が面談中に何度も繰り返される場合は、時系列ではなく内容を統合する
- 本題と関係のない雑談は主要な分析対象から除外する
- 不明な内容をもっともらしく推測しない

出力は、後続の要約処理で使用するため、
情報を省略しすぎず、詳細な構造化データとして出力してください。

文字起こし:
{transcript}
------------------------------------------------------------


============================================================
5. Step 1の出力イメージ
============================================================

最終仕様は今後検討するが、概念的には以下のようなJSONを想定する。

{
  "metadata": {
    "source_type": "transcript",
    "conversation_type": "performance_interview"
  },
  "conversation_overview": {
    "purpose": "",
    "summary": ""
  },
  "topics": [
    {
      "title": "",
      "issue": "",
      "facts": [],
      "participant_statements": [],
      "interviewer_statements": [],
      "background_or_causes": [],
      "final_recognition": [],
      "improvement_actions": [],
      "uncertainties": []
    }
  ],
  "overall_themes": [],
  "decisions": [],
  "actions": [],
  "open_questions": [],
  "uncertain_points": []
}

重要:
JSONのスキーマは現時点では確定しない。
ALICE_Summary v1.0の実装時に、Transcript/Minute/Memoryとのインターフェースを
含めて設計する。


============================================================
6. Step 2: 人間向け要約の生成
============================================================

Step 1の構造化結果を入力として、人間が読みやすい要約を生成する。

ここでは生の文字起こしを直接要約するのではなく、
すでに理解・整理されたデータから文章を構成する。

推奨プロンプト例:

------------------------------------------------------------
あなたは面談内容を客観的かつ正確に要約するAIです。

以下は、面談文字起こしを詳細に分析・構造化した結果です。

この情報だけを根拠として、面談全体の内容を分かりやすく要約してください。

単なる発言の時系列要約ではなく、

- この面談は何のために行われたのか
- どのような問題が取り上げられたのか
- 各問題について、本人はどのように説明したのか
- 面談者側は何を問題視していたのか
- 面談を通して、どのような共通課題が明らかになったのか
- 最終的に何が決まり、今後どうすることになったのか

が理解できるように整理してください。

以下の構成で出力してください。

# 面談の目的

# 主な議題

## 議題1
### 確認された内容
### 本人の説明・認識
### 面談者側の指摘
### 整理された課題

## 議題2
...

# 面談全体を通じた共通課題

# 最終的な結論・今後の対応

# 一言でまとめると

重要なルール:

- 入力にない事実を追加しない
- AI独自の推測を事実として書かない
- 「本人が言ったこと」と「面談者が評価したこと」を区別する
- 必要に応じて内容を統合してよいが、意味を変えない
- 同じ内容の繰り返しはまとめる
- 終盤の雑談は除外する
- 読者が面談に参加していなくても全体像を理解できるようにする

分析結果:
{analysis_result}
------------------------------------------------------------


============================================================
7. Step 3: 原文との整合性チェック
============================================================

重要な面談、評価面談、人事面談などでは、要約の誤りが大きな問題になる。

そのため必要に応じて、生成された要約を原文と比較する
Consistency Checkerを実行する。

推奨プロンプト例:

------------------------------------------------------------
以下の「元の文字起こし」と「作成された要約」を比較してください。

要約について、以下を確認してください。

1. 元の文字起こしに存在しない事実が追加されていないか
2. 本人の発言と面談者側の指摘が混同されていないか
3. 面談者の評価が客観的事実として書かれていないか
4. 重要な議題や結論が抜けていないか
5. 後半で訂正・修正された内容が反映されているか
6. 雑談が本題として含まれていないか
7. 推測が断定的に書かれていないか

問題がある場合は修正してください。

問題がない場合は、内容を変更せずそのまま出力してください。

元の文字起こし:
{transcript}

作成された要約:
{draft_summary}
------------------------------------------------------------


============================================================
8. 精度を上げる上での重要ポイント
============================================================

(1) 「要約」と「理解」を分離する

悪い例:
Transcript → 直接要約

推奨:
Transcript → 会話理解/構造化 → 要約

Gemma 4:12Bには、理解・分析・文章化を一度に要求するより、
役割を分離した方が安定する可能性が高い。


(2) 事実と評価を分離する

特に面談・評価・人事系の会話では重要。

例:

・客観的事実
  「遅刻が発生した」

・本人の説明
  「本人は寝坊が原因だったと説明した」

・面談者の評価
  「面談者は危機感が不足していると指摘した」

・AIの分析
  「複数の問題に、改善行動への移行が遅いという共通傾向が見られる」

これらを混同しない。


(3) 「後半の訂正」を重視する

長時間の面談では、最初の回答が後から修正される場合がある。

例:
最初は「計画的に対策していた」と説明
↓
後半の掘り下げで
「実際には問題が起きるたびにその場で考えていた」
と修正

この場合、最終的な理解・認識を反映する必要がある。


(4) 推測を事実として書かない

文字起こしが荒れている場合、AIは空白をもっともらしく補完しやすい。

「合理的に思える」ことと
「文字起こしから確認できる」ことは別である。

判断できない場合は不明として残す。


(5) 中間成果物を残す

summary.jsonを残すことで、

・要約の再生成
・別フォーマットへの変換
・Minute生成
・Memory候補抽出
・Task抽出
・Insight分析

などに再利用できる。


============================================================
9. ALICE_Summaryの位置づけ
============================================================

ALICE_Summaryは、単なる短縮要約モジュールではなく、

「Transcriptを、ALICEが後続処理で利用できる意味理解済みデータに変換する層」

として考える。

イメージ:

人間の会話
    ↓
ALICE_Transcript
    ↓
文字起こしデータ
    ↓
ALICE_Summary
    ↓
意味理解・構造化データ
    ├── ALICE_Minute
    ├── ALICE_Memory
    ├── Task抽出
    ├── ALICE_Insight
    └── ALICE_Search

この構成にすると、ALICE_Minuteは
「生の文字起こしを理解するモジュール」ではなく、
「理解済みデータから目的別の文書を生成するモジュール」
として責務を明確化できる。


============================================================
10. 推奨する初期実装方針
============================================================

まずはALICE_Summary v1.0として、以下を目標にする。

Input:
    transcript.json

Process:
    1. LLMによる会話理解・構造化
    2. LLMによる人間向け要約生成

Output:
    summary.json
    summary.md

重要案件のみ:
    3. 原文との整合性チェック

この時点では、いきなりMemory、Task、Insightとの統合を実装しない。

まず、
「荒れた長時間文字起こしから、ChatGPTに近い品質の要約を
Gemma 4:12Bでどこまで安定して生成できるか」
を検証する。

評価の際には、以下を確認する。

・主要議題の抽出漏れ
・重要な結論の欠落
・事実と評価の混同
・本人が発言していない内容の追加
・後半の訂正の反映
・雑談の混入
・文章としての読みやすさ
・ChatGPTによる参照要約との差分

============================================================
12. 結論
============================================================

ChatGPTに近い精度の要約をGemma 4:12Bで目指す場合、
単純な「高性能な要約プロンプト」を作るのではなく、

1. 会話を理解する
2. 理解結果を構造化する
3. 構造化結果から要約を書く
4. 必要に応じて原文と照合する

という段階的な処理フローを採用する。

最重要ポイントは、

「要約する前に、まず会話を理解させる」

ことである。

この思想はALICE_Summaryを、単なる要約機能ではなく、
TranscriptとMinute/Memory/Insight等の間に位置する
「意味理解層」として発展させる可能性がある。

現時点では仮説・設計メモとして保存し、
Memory v1.0の稼働およびCore/Transcript/Minute統合後、
ALICE_Summaryの設計・実装時に改めて検証する。
