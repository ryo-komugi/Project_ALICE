# ADR 007: ナレッジ検索基盤における SQLite FTS5 (trigram) 転置インデックスと派生キャッシュアーキテクチャの採択

> Status: Accepted  
> Date: 2026-09-11  
> Deciders: Project_ALICE Core Architecture Team  

---

## 1. 背景と課題 (Context)

Project_ALICE の運用に伴い、日々の音声会話から文字起こし（`transcript.txt`）および高品質要約（`summary.txt`, `summary.md`）が Workspace 内に蓄積されてきた。ユーザーが過去の会話・決定事項・トピックを即座に再探索・参照したいというニーズが高まった。

この検索基盤の設計にあたり、以下の選択肢と課題が存在した：
1. **Vector DB / RAG / Embedding モデルの導入**:
   - セマンティック検索が可能だが、モデルのメモリ消費（GPU/RAM圧迫）、依存関係の複雑化、チャンキング設計や更新コストなどの過剰設計（Over-engineering）が生じる。
2. **既存 WorkspaceManager による線形走査 ($O(N)$)**:
   - 全ファイルを逐次ファイルリードするため、件数増加に伴い著しく低速化する。
3. **耐障害性とデータ正本性の維持**:
   - 検索用データベースが破損した場合にデータロストが発生してはならない。また、検索インデックスの更新失敗によって Job 全体が失敗扱いに巻き込まれる事故を防止する必要がある。

---

## 2. 決定事項 (Decision)

以下のアーキテクチャを採用することを決定した。

### 1. SQLite FTS5 (trigram) による独立検索エンジン (`ALICE_Search`)
- 外部サーバーや追加の重厚なデーモンを必要とせず、Python 標準ライブラリと SQLite 拡張機能（FTS5）のみで完結する `ALICE_Search` を独立モジュールとして実装する。
- 日本語・英数字が混在する長文に対応するため、トークナイザーには形態素解析器の外部依存が不要な **`trigram` (3-gram)** を採用する。
- 3 文字未満の短いキーワード（「AI」「予算」等）については、FTS5 テーブルに対する `LIKE '%...%'` スキャンへの自動フォールバックとハイライト補完を行い、検索漏れを防止する。

### 2. Workspace = Source of Truth、DB = 派生キャッシュ（Derived Cache）
- すべてのジョブ成果物の正本（一次データ）は、永続的に各 Workspace 内に保持される。
- SQLite データベース（`/data/runtime/search/alice_index.db`）は、高速検索のために用意された「いつでも 100% 再構築可能な派生キャッシュ（Secondary Index）」と定義する。万が一 DB が破損しても、`python cli.py --reindex` により全件復旧可能とする。

### 3. Job 成否と Index 更新成否の完全分離（成否境界）
- CoreWorker のパイプラインにおいて、成果物の生成・検証およびユーザー（LINE）への配信が完了した時点で Job は `COMPLETED` と確定する。
- インデックス更新はその後に行われる非ブロッキング派生処理とし、更新エラーが発生しても Job の成功ステータスは絶対に覆さない。

### 4. Workspace Driven CLI 連携
- `ALICE_Core` および `ALICE_CoPilot` との連携は、クラスの import ではなく CLI（`python cli.py --query "..."` / `--index-job <path>`）を介して行う。

---

## 3. 影響と評価 (Consequences)

### メリット
- **極めて軽量かつ堅牢**: GPU リソースを一切消費せず、数千件規模の会話成果物をミリ秒単位で全文検索・BM25 ランキング可能。
- **ゼロデータロスト保証**: 正本がファイルシステム上に独立しているため、DB トラブルがデータ損失に直結しない。
- **疎結合の維持**: Core や CoPilot に検索ロジックが侵食せず、各モジュールの責務が明確に分離される。

### デメリット / 制約事項
- **意味的類似検索（Semantic Search）の非対応**: キーワードの一致が前提となり、「言い換え」による曖昧検索は行えない（※v1.0 では現実的な実用性・レスポンス速度を最優先し、Vector/RAG は将来の拡張として見送る）。
